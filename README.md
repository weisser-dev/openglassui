# OpenGlassUI

[Try the interactive demo](https://weisser-dev.github.io/openglassui/) · [Installation](#local-setup) · [Architecture](docs/ARCHITECTURE.md)

The public demo uses fictional data and runs entirely in the browser; it does not connect to agents or control a local machine. It is not the installable glasses app: generate the app's QR code in your local companion setup instead.

A local control center for coding agents, with an experimental web interface for Meta Ray-Ban Display glasses. OpenGlassUI runs a companion service on your computer: configure your workspace and agents there, then use the desktop dashboard or a paired glasses web app to follow tasks and respond to supported questions.

> **Status: early prototype.** Local Codex task creation, continuation, and an interactive multiple-choice question have been exercised with a real Codex installation. Claude Code's real end-to-end flow, the Meta AI installation link, the wristband, and WebMCP have **not** been verified on physical glasses. Do not treat the current remote-access design as production-ready.

## What works today

| Capability | Current implementation | Limits |
| --- | --- | --- |
| Local dashboard | Start and stop tasks, view output, and continue supported sessions | The current interface and agent instructions are in German |
| Codex | Local app-server adapter, output, session browser, follow-up turns, supported questions and one-time approvals | Uses the experimental `default_mode_request_user_input` flag; supported request types and Codex versions may change |
| Claude Code | Claude Agent SDK adapter, session browser, follow-up turns, question and permission callbacks | Adapter flows have automated tests with a simulated SDK. A real run failed because the test machine's OAuth session had expired; reauthentication and end-to-end validation are still needed |
| Kiro CLI | ACP V3 adapter with session browsing, task execution, tool-event timeline, one-time permissions and reported usage | A real task, tool events, context usage and resume were tested locally; real permission handling and visual usage display need further end-to-end verification |
| Other CLIs | Configurable command and arguments; prompts are sent via stdin without a shell | The program must accept stdin. Output is raw; there is no generic session discovery or interactive decision support |
| Glasses and voice | Experimental glasses page, per-device pairing, project selection, in-app notices, optional Web Push, directional-key handling, and WebMCP tools | Requires an HTTPS tunnel; device installation, gesture handling, dictation, background push, and Meta AI availability are unverified |

For new Codex and Claude tasks, the adapters ask the agent to present concise options when user input is needed. Suggestions are generated by the agent from its available context and are not guaranteed for every question. Explicit approvals are presented separately and are not automatically granted.

## How it fits together

See [architecture and trust boundaries](docs/ARCHITECTURE.md) for the full diagram.

```text
Desktop dashboard ── localhost admin ──┐
                                       ├── companion ── agent adapters
Glasses ── HTTPS tunnel ── gateway ────┘                 (Codex / Claude / Kiro / other CLI)
```

The companion owns the workspace and agent configuration, launches agents locally, and stores task data on the computer. The glasses page communicates with that companion through a separately configured HTTPS tunnel. The QR code is an installation and pairing link; it does not create the tunnel. The dashboard can start an installed Cloudflare, ngrok, or Tailscale Serve client on demand. A separate gateway listener is used for remote access.

## Requirements

- Node.js 20 or later and npm.
- A supported agent installed, authenticated, and available to the local user. Codex requires the `codex` executable; the Claude adapter uses the Claude Agent SDK and its supported authentication. Verify your provider's current authentication and usage requirements.
- For glasses: Meta Ray-Ban Display, an iPhone with the Meta AI app, access to the necessary developer/web-app settings, and a public HTTPS endpoint connected to the companion.
- For the example tunnel below: [cloudflared](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/downloads/).

Meta's device capabilities, developer settings, and WebMCP availability may vary by account, region, firmware, and rollout. A desktop browser test does not verify device behavior.

## Local setup

Clone the repository and install dependencies:

```sh
git clone https://github.com/weisser-dev/openglassui.git
cd openglassui
npm ci
```

Create a local configuration from the example and adjust it for your machine:

```sh
cp config.example.json config.json
```

On Windows, copy `config.example.json` to `config.json` using Explorer or your shell. Alternatively, `./setup.sh` on macOS/Linux or `setup.bat` on Windows installs dependencies and creates the configuration if it does not already exist. On macOS, `Install-OpenGlassUI.command` and `Start-OpenGlassUI.command` can also be opened from Finder; Windows users can run `setup.bat` and `Start-OpenGlassUI.bat`. These are scripts, not signed native installers, and platform-specific execution still needs verification.

Set `workspace` to the project the agents should work in. A relative path is resolved relative to the configuration file. Configure the agent IDs, executable names, and arguments under `agents`; `config.json` is ignored by Git. Agent sign-in, provider settings, and permission policies remain the responsibility of the respective tools.

Start the companion:

```sh
npm start
```

Open [http://127.0.0.1:4173](http://127.0.0.1:4173). The dashboard also contains a step-by-step glasses installation guide. Use **Bestehende Sitzungen** to browse Codex, Claude or Kiro sessions returned for the selected workspace. Large session lists can take time to load. Add more projects locally via **Projekt hinzufügen**; registered projects can then be selected on the glasses. Only continue sessions that are no longer active elsewhere; attaching safely to an externally running session is not supported. Open **Brillen-Simulator** for a keyboard-driven preview using live data.

The setup has five main steps. You can select multiple agents, review and import selected discovered projects for each agent, start an installed tunnel or enter an HTTPS address, generate a pairing QR code, and check for a paired device. The wizard saves non-secret selections locally in `.openglass/setup.json`; provider authentication is handled separately. If Tailscale requires Serve activation, the setup provides its authorization link and resumes once approved; HTTPS may also need to be enabled. A detected pairing does not establish that the glasses display or wristband works. The setup supports English and partial German translations; the rest of the interface has not yet been fully migrated to internationalization.

In **Bestehende Sitzungen**, select an agent and choose **Alle Sitzungen suchen** to discover its locally available sessions across projects. Results are visible only on the local dashboard. Choosing a result registers its project if necessary and opens the session; registered projects become available to paired devices. Sessions without a known, accessible local working directory are excluded. Providers can differ in which historical sessions they expose; continuing a session still requires the agent's own authentication and support.

### Configuration details

`config.example.json` provides Codex, Claude Code, and Kiro examples. For a custom CLI, add an object with `id`, `name`, `command`, an `args` array, and `input: "stdin"`. The configured command receives the task through stdin and is started with `shell: false`. Only install or configure executables you trust: these agents run with the local user's privileges and their own permission settings.

Codex and Claude are special adapters selected by the IDs `codex` and `claude`; they do not use the generic CLI path. Codex uses `command` to start its app-server. Claude is launched through the Agent SDK rather than the configured `command`. The current server still requires valid `args`, `input`, and `command` fields for both; `resumeArgs` must be present for the resume action to be offered. Changing those CLI argument arrays does not configure the special adapters. Kiro uses ACP V3, launched as `kiro-cli acp --agent-engine v3`; its optional `acpArgs` config overrides those arguments. Other CLI entries use the generic command and arguments and currently have no way to discover a session ID for resume.

Optional environment variables:

| Variable | Purpose | Default |
| --- | --- | --- |
| `PORT` | Local HTTP port | `4173` |
| `OPENGLASS_GATEWAY_PORT` | Loopback gateway port to forward through the tunnel | `PORT + 1` (normally `4174`) |
| `OPENGLASS_CONFIG` | Path to a JSON configuration file | `config.json` in the project directory |
| `OPENGLASS_DATA_DIR` | Directory for local task data | `.openglass/` in the project directory |

Both the admin service and gateway bind to `127.0.0.1`, not the local network. Tasks and their output are written to `.openglass/tasks.json` by default, including prompts and potentially sensitive agent output. Data is not encrypted at rest. Running tasks are marked interrupted after a server restart.

## Connect the glasses (experimental)

1. Enable the developer/web-app options required by Meta AI for your glasses.
2. Start OpenGlassUI and leave it running on the computer.
3. In the dashboard, select an installed tunnel provider and click **Tunnel starten**. Alternatively, in a second terminal create an HTTPS tunnel, for example with cloudflared and the default port:

   ```sh
   cloudflared tunnel --url http://127.0.0.1:4174
   ```

   Copy the HTTPS URL printed by cloudflared. If you changed `OPENGLASS_GATEWAY_PORT`, use that port in the command. Never forward the admin port. Cloudflare describes Quick Tunnels as a development feature; the address changes when the tunnel is restarted. See the [Quick Tunnel documentation](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/).

   For private access, select **Tailscale Serve** instead. Install and sign in to Tailscale on the companion and iPhone, enable HTTPS in the tailnet, and allow access under your tailnet policy. Tailscale is required only for this option, not when using Cloudflare or ngrok. The dashboard starts foreground `tailscale serve` for the gateway; stopping it ends that foreground service. A conflicting existing Serve configuration may need separate attention. The glasses' ability to reach a private tailnet address through the iPhone has not been verified; connecting from the iPhone alone does not prove glasses connectivity. If the glasses report that the app cannot load, try the generated app URL on the iPhone first; an iPhone-only success still does not establish glasses access. For an initial device test, a publicly reachable HTTPS tunnel follows Meta's documented web-app deployment path. See [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve).
4. In the desktop dashboard, paste that address into **ÖFFENTLICHE HTTPS-ADRESSE** and choose **Kopplungscode erzeugen**.
5. Scan the QR code with the iPhone, follow the Meta AI app's add-web-app flow, and open OpenGlassUI on the glasses **within five minutes**. The pairing code can be redeemed once. This deep-link flow is implemented but has not been verified on the actual device.
6. Keep the companion and tunnel running while using the app. An Internet connection is needed for the tunnel; the glasses and computer do not need to be on the same LAN when the HTTPS endpoint is reachable.

The glasses page organizes agents, projects and chats into navigable screens, with a conversation view and settings. It uses authenticated WebSocket revision events with long-poll fallback and implements geometry-based directional navigation and Select. Text fields use the host's standard text composer; Meta documents handwriting and voice composition on supported glasses. Camera attachments are not implemented. In settings, a paired device can optionally subscribe to standard Web Push after the wearer grants browser permission. The implementation has mock-based tests, but Web Push availability and delivery on Meta glasses have not been established. Meta documents that WebMCP tools are available only while the web app is in the foreground, with a 10-second call deadline. It also registers experimental WebMCP tools when `document.modelContext` is available. The complete navigation, text composition and gestures need a real-device test. See [Meta's web-app input guidance](https://github.com/meta/meta-wearables-webapp/blob/main/plugins/meta-wearables-webapp/skills/ai-glasses-webapp-device/SKILL.md).

The chat composer presents dictation or handwriting as the primary action. Select the field to open the device's composer; a web page cannot open it automatically. Back navigation handles Escape and browser history, restores the originating focus and scroll position, and leaves Backspace available for text editing. An in-app back button remains available while device gesture behavior is being verified. Meta documents the thumb-to-middle-finger gesture for back navigation; behavior in the device composer and on physical glasses still needs verification. Usage and tool activity are hidden by default and can be enabled in glasses settings. Read-aloud is also off by default; manual and automatic playback depend on the device browser's speech synthesis support, which has not yet been verified on Meta glasses.

When speech synthesis is available, the glasses settings offer device-default, German and English speech languages. OpenGlassUI requests a matching device voice if one is reported; available voices and accents depend on the device, and the selection does not translate the response.

After setup is completed, subsequent visits open the dashboard directly; setup remains available from the dashboard. Configuration, paired-device records and task history are stored locally in the ignored `.openglass` directory (or `OPENGLASS_DATA_DIR`), currently as JSON rather than SQLite. The dashboard counts locally stored tasks, pending decisions and prompts sent through OpenGlassUI since message tracking was introduced. It does not count historical messages or activity in other clients. Token and cost figures are shown per task only when reported by the provider; their scope varies by provider. Effective agent permissions and comprehensive MCP usage are not currently available. This activity information stays local to the companion and is not sent to an analytics service.

The gateway also serves Meta's `/.well-known/meta-wearables-manifest.json` and a monochrome glasses icon for the launcher. An existing installation may need to be removed and added again to refresh its icon; actual launcher rendering has not yet been verified on hardware. See Meta's [app icon utility](https://github.com/meta/meta-ray-ban-display-ui-toolkit-web/tree/main/examples/app-icon-generator).

## Security and privacy

**This is an experimental single-user prototype, not a hardened remote-access service.**

- The companion binds to localhost. Remote access depends on a correctly configured HTTPS reverse proxy. The companion separates the admin listener from a paired-device gateway. Forward only the gateway port through a tunnel; never publish the admin port. A malicious local process can still access the admin listener, and this design is not a formal security audit.
- A pairing QR contains a short-lived secret. Anyone who redeems it can read accessible tasks and sessions and launch configured agents with the permissions of the local user. Treat the QR and installation link like a password; do not share screenshots or logs containing them.
- The companion issues a bearer token to a paired device. It is stored in that device's browser storage and is not hardware-bound. Its hash and device metadata persist locally until revoked. Revoke devices individually or use **Alle Verbindungen trennen** in the local dashboard. The token grants access to all registered projects and tasks.
- Optional Web Push stores a browser push subscription and local VAPID private key in the protected data directory; the browser push provider receives encrypted generic event notifications and connection metadata. Payloads contain no project names, prompts, paths, or agent output. Only supported browser-vendor push endpoints are accepted. Delivery requires a running companion and is not guaranteed. The local dashboard reports provider acceptance or failure; acceptance does not prove the wearer saw the notification, and already queued messages can arrive briefly after revocation. Browser support, permission behavior, and background delivery on Meta glasses are unverified. Revoking a paired device removes its server-side subscription.
- Remote task data and agent outputs pass through the HTTPS tunnel provider. Local task data is stored without encryption. Consider what code, prompts, and output the agent and tunnel provider can access.
- Approvals are per request where supported. Existing agent configuration may already allow actions without a prompt. OpenGlassUI does not guarantee a separate confirmation for every action.

## Current technical gaps

- **Physical device validation:** QR deep link, setup, layout, focus order, wristband gestures, text input, WebMCP, reconnection, and long-running use need testing on actual Meta Ray-Ban Display hardware.
- **Installation and hosting:** Setup scripts and on-demand tunnel start exist, but no signed native installer, automatic updates, stable hosted URL, background service, or managed reverse-proxy access control. Tunnel clients must be installed and ngrok authenticated separately.
- **Sessions:** No reliable live takeover of sessions running in other clients, no pagination beyond the first 50 sessions, and no full transcript navigation or search. Generic CLI sessions cannot currently be resumed through the app.
- **Questions and permissions:** Simultaneous requests are queued per task and displayed one at a time; complete multi-select handling is still missing. Not every Codex server-request type is supported. AI-generated choices depend on the agent and may be absent.
- **Security:** No hardware-bound credentials, encrypted client storage, granular authorization, formal security review, or production-grade proxy authentication. The current deployment must remain a trusted, experimental single-user setup.
- **Reliability and UX:** No agent health checks, task deletion, reliable child-process-tree termination, comprehensive accessibility testing, or English UI. Kiro and Codex tool events are shown as a bounded per-task timeline; Claude and generic CLI agents do not yet have structured timelines. Outputs are bounded and may be truncated.
- **Testing:** Automated tests simulate agent decision paths and tunnel processes. A real Kiro task through the companion API, tool events, context usage, session list, and continuation were checked locally; a real Claude account, end-to-end tunnel traffic, WebMCP, simulator interaction, and physical glasses still need verification. Cloudflare Quick Tunnel startup was exercised locally against an isolated test target.

## Tests

```sh
npm test
```

The suite exercises the local API, project allowlist, pairing and revocation, separate gateway, authenticated WebSocket revocation, tunnel manager, opt-in Web Push validation and mock delivery, simulated Codex, Claude and Kiro decision handling, a paired Kiro event-to-decision flow, foreground-notification transitions, spatial navigation logic, usage formatting and voice-tool validation. It requires permission to bind a localhost port. A successful suite is not a substitute for hardware or provider end-to-end testing.

If Claude reports that its OAuth session has expired, authenticate again using the supported Claude Code login flow, for example `claude auth login` where available, then retry. OpenGlassUI does not request or store your Claude password.
