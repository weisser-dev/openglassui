# OpenGlassUI

[Try the interactive demo](https://weisser-dev.github.io/openglassui/) · [Documentation](https://weisser-dev.github.io/openglassui/docs.html) · [Privacy](https://weisser-dev.github.io/openglassui/privacy.html) · [Changelog](CHANGELOG.md) · [Installation](#local-setup) · [Architecture](docs/ARCHITECTURE.md)

The public demo uses fictional data and runs entirely in the browser; it does not connect to agents or control a local machine. It is not the installable glasses app: generate the app's QR code in your local companion setup instead.

OpenGlassUI connects wearables and desktop clients to locally configured coding-agent harnesses, with an experimental web interface for Meta Ray-Ban Display glasses. OpenGlassUI runs a companion service on your computer: configure your workspace and agents there, then use the desktop dashboard or a paired glasses web app to follow tasks and respond to supported questions.

> **Status: early prototype.** Local Codex task creation, continuation, and an interactive multiple-choice question have been exercised with a real Codex installation. Claude Code's real end-to-end flow, the Meta AI installation link and basic wristband navigation have been exercised by a wearer. WebMCP, background push, and complete end-to-end flows remain unverified on physical glasses. Do not treat the current remote-access design as production-ready.

## What works today

| Capability | Current implementation | Limits |
| --- | --- | --- |
| Local dashboard | Start and stop tasks, view output, and continue supported sessions | The current interface and agent instructions are in German |
| Codex | Local app-server adapter, output, session browser, follow-up turns, supported questions and one-time approvals | Uses the experimental `default_mode_request_user_input` flag; supported request types and Codex versions may change |
| Claude Code | Claude Agent SDK adapter, session browser, follow-up turns, question and permission callbacks | Adapter flows have automated tests with a simulated SDK. A real run failed because the test machine's OAuth session had expired; reauthentication and end-to-end validation are still needed |
| Kiro CLI | ACP V3 adapter with session browsing, task execution, tool-event timeline, one-time permissions and reported usage | A real task, tool events, context usage and resume were tested locally; real permission handling and visual usage display need further end-to-end verification |
| OpenCode | Experimental ACP adapter for task execution, session discovery and one-time permission requests | Local ACP session listing has been exercised; real task execution, permissions and continuation still need end-to-end verification. Uses the OpenCode configuration and model provider. |
| Other CLIs | Configurable command and arguments; prompts are sent via stdin without a shell | The program must accept stdin. Output is raw; there is no generic session discovery or interactive decision support |
| Glasses and voice | Experimental glasses page, per-device pairing, project selection, in-app notices, optional Web Push, directional-key handling, and WebMCP tools | Requires an HTTPS tunnel; device installation, gesture handling, dictation, background push, and Meta AI availability are unverified |

For new Codex and Claude tasks, the adapters ask the agent to present concise options when user input is needed. Suggestions are generated by the agent from its available context and are not guaranteed for every question. Explicit approvals are presented separately and are not automatically granted.

OpenCode can connect model providers through its own configuration, including OpenAI, Anthropic, Google, DeepSeek and OpenAI-compatible providers. Provider connectivity does not by itself add a standalone agent adapter to OpenGlassUI. See [OpenCode provider configuration](https://opencode.ai/docs/providers) and [ACP support](https://opencode.ai/docs/cli/acp/). Codex and Claude Code can offer model selection when their catalogs are available. Kiro CLI V3, OpenCode and generic ACP agents can offer it for a subsequent turn when they advertise ACP model options. Availability depends on the agent and account; actual device and provider end-to-end behavior still needs verification.

The paired-device chat separates newly recorded user and agent messages. Earlier mixed output is labelled as a transcript. The public demo is built from the same wearable UI with fictional local data; run `node scripts/build-demo.js` before serving the `demo` directory.

## Add another ACP coding agent

Open the setup wizard and choose **Add an ACP-compatible agent**. Enter a display name, the installed executable and its arguments as a JSON array, for example `["acp"]` if that is what the agent documents. The command is started without a shell. The local companion stores the entry in `.openglass/acp-agents.json`; do not put API keys or passwords in command-line arguments. Reopen setup to select the agent and approve projects.

The generic adapter supports ACP v1 text prompts, streamed text, tool progress, cancellation, model options, session listing/loading when the agent advertises them, and supported one-time approval choices. Not all ACP features or extensions are implemented: agents requiring client-side filesystem or terminal RPCs, unsupported permission modes, authentication prompts, or other protocol extensions may not work. Existing Kiro, OpenCode, Codex and Claude adapters remain separate. Generic ACP agents are executable programs with the local user's privileges: configure trusted programs only.

### LiteLLM and model providers

[LiteLLM AI Gateway](https://docs.litellm.ai/docs/simple_proxy) can route a compatible harness's model requests to many configured model providers. It is a gateway, not a replacement for the coding harness that manages files, tools, sessions and approvals. Configure LiteLLM in the agent itself, such as an OpenCode provider, following the [LiteLLM client setup](https://docs.litellm.ai/docs/proxy/client_setup/overview) and the agent's documentation; then connect that agent to OpenGlassUI through its native adapter or ACP. OpenGlassUI does not install or configure LiteLLM, manage gateway credentials, guarantee every provider feature, or offer a direct LiteLLM chat adapter. Routing, provider privacy, logging and costs depend on the selected services and configuration.

## How it fits together

See [architecture and trust boundaries](docs/ARCHITECTURE.md) for the full diagram and [agent client integration](docs/AGENT_CLIENTS.md) for the internal interface and contribution guidance.

```text
Desktop dashboard ── localhost admin ──┐
                                       ├── companion ── agent adapters
Glasses ── HTTPS tunnel ── gateway ────┘                 (Codex / Claude / Kiro / other CLI)
```

The dashboard counts requests submitted by paired devices and successful completions after this feature was added. It cannot distinguish a paired phone from glasses, and earlier activity is not reconstructed. Device last activity records authenticated requests or an active connection, not confirmed physical presence.

OpenGlassUI is a control surface and local companion: the connected agent owns its model, provider authentication, tools and permission policy. OpenGlassUI launches agents locally and currently stores configuration, paired-device records, task prompts, outputs and conversation history on the computer; it is not a config-only proxy. The glasses page communicates with that companion through a separately configured HTTPS tunnel. The QR code is an installation and pairing link; it does not create the tunnel. The dashboard can start an installed Cloudflare, ngrok, or Tailscale Serve client on demand. A separate gateway listener is used for remote access.

## Requirements

- Node.js 20 or later and npm.
- A supported agent installed, authenticated, and available to the local user. Codex requires the `codex` executable; the Claude adapter uses the Claude Agent SDK and its supported authentication. Verify your provider's current authentication and usage requirements.
- For glasses: Meta Ray-Ban Display, an iPhone with the Meta AI app, access to the necessary developer/web-app settings, and a public HTTPS endpoint connected to the companion.
- For the example tunnel below: [cloudflared](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/downloads/).

Meta's device capabilities, developer settings, and WebMCP availability may vary by account, region, firmware, and rollout. A desktop browser test does not verify device behavior.

## Local setup

### npm package

Install the published `@weisser-dev/openglassui` package with `npm install -g @weisser-dev/openglassui` and start it with `openglassui`. The package stores its configuration and local data in `~/.openglassui`; the current directory becomes the initial default project. Use `OPENGLASS_CONFIG` and `OPENGLASS_DATA_DIR` to override those paths.

The setup wizard has separate opt-in switches for starting OpenGlassUI at user login (macOS only) and starting the selected tunnel when the companion starts. The login item takes effect at the next login and points to the current Node executable and installation path; reconfigure it after moving or removing either. Automatic tunnel start requires a completed setup. A public tunnel exposes the gateway and Cloudflare Quick Tunnel addresses change on restart.

### Install from source

Clone the repository and install dependencies:

```sh
git clone https://github.com/weisser-dev/openglassui.git
cd openglassui
npm ci
```

Create a local configuration from the example and adjust it for your machine:

```sh
cp config.example.json config.json
```

On Windows, copy `config.example.json` to `config.json` using Explorer or your shell. Alternatively, `./setup.sh` on macOS/Linux or `setup.bat` on Windows installs dependencies and creates the configuration if it does not already exist. On macOS, `Install-OpenGlassUI.command` and `Start-OpenGlassUI.command` can also be opened from Finder; Windows users can run `setup.bat` and `Start-OpenGlassUI.bat`. These are scripts, not signed native installers, and platform-specific execution still needs verification.

Set `workspace` to the project the agents should work in. A relative path is resolved relative to the configuration file. Configure the agent IDs, executable names, and arguments under `agents`; `config.json` is ignored by Git. Agent sign-in, provider settings, and permission policies remain the responsibility of the respective tools.

Start the companion:

```sh
npm start
```

Open [http://127.0.0.1:4173](http://127.0.0.1:4173). The dashboard also contains a step-by-step glasses installation guide. Use **Bestehende Sitzungen** to browse Codex, Claude or Kiro sessions returned for the selected workspace. Large session lists can take time to load. Add more projects locally via **Projekt hinzufügen**; registered projects can then be selected on the glasses. Only continue sessions that are no longer active elsewhere; attaching safely to an externally running session is not supported. Open **Brillen-Simulator** for a keyboard-driven preview using live data.

The setup has six main steps. You can select multiple agents, review and import selected discovered projects for each agent, start an installed tunnel or enter an HTTPS address, optionally install cloudflared with Homebrew on macOS or opt in to starting the selected tunnel on companion startup, generate a pairing QR code, choose automatic login and tunnel startup, and check for a paired device. The wizard saves non-secret selections locally in `.openglass/setup.json`; provider authentication is handled separately. If Tailscale requires Serve activation, the setup provides its authorization link and resumes once approved; HTTPS may also need to be enabled. A detected pairing does not establish that the glasses display or wristband works. The setup supports English and partial German translations; the rest of the interface has not yet been fully migrated to internationalization.

In **Bestehende Sitzungen**, select an agent and choose **Alle Sitzungen suchen** to discover its locally available sessions across projects. Results are visible only on the local dashboard. Choosing a result registers its project if necessary and opens the session; registered projects become available to paired devices. Sessions without a known, accessible local working directory are excluded. Providers can differ in which historical sessions they expose; continuing a session still requires the agent's own authentication and support. Claude session imports show up to the most recent 100 text messages; tool-only events do not displace conversation text. Imported Claude Code and Codex conversations are monitored read-only while the companion runs. It checks up to five distinct sessions every ten seconds, so updates can take longer when many sessions are imported. Other providers remain snapshots. This does not take over the external client or expose its approval requests; background notifications depend on device support. When Kiro reports a session status, the interface shows it as a provider-reported snapshot at lookup time, not verified live activity.

### Configuration details

`config.example.json` provides Codex, Claude Code, and Kiro examples. For a custom CLI, add an object with `id`, `name`, `command`, an `args` array, and `input: "stdin"`. The configured command receives the task through stdin and is started with `shell: false`. Only install or configure executables you trust: these agents run with the local user's privileges and their own permission settings.

Codex and Claude are special adapters selected by the IDs `codex` and `claude`; they do not use the generic CLI path. Codex uses `command` to start its app-server. Claude is launched through the Agent SDK rather than the configured `command`. The current server still requires valid `args`, `input`, and `command` fields for both; `resumeArgs` must be present for the resume action to be offered. Changing those CLI argument arrays does not configure the special adapters. Kiro uses ACP V3, launched as `kiro-cli acp --agent-engine v3`; its optional `acpArgs` config overrides those arguments. Other CLI entries use the generic command and arguments and currently have no way to discover a session ID for resume.

Optional environment variables:

| Variable | Purpose | Default |
| --- | --- | --- |
| `PORT` | Local HTTP port | `4173` |
| `OPENGLASS_GATEWAY_PORT` | Loopback gateway port to forward through the tunnel | `PORT + 1` (normally `4174`) |
| `OPENGLASS_CONFIG` | Path to a JSON configuration file | `config.json` in the project directory |
| `OPENGLASS_DATA_DIR` | Directory for local task data | `.openglass/` in the project directory |

### Wearable chat shortcuts

On a recent chat, swipe left to reveal the crossed-out eye, then select it to hide the chat from the home screen. The session itself remains available under its agent and project. Restore hidden chats under Settings → Recent chats. Long-press detection depends on the device host and is not required. These preferences and cached session titles are stored locally in the web app's origin and do not automatically transfer to another URL or device.

For a chat from any supported agent, **Suggest replies** sends a bounded selection of the most recent conversation messages to a separate, tool-free Claude turn. Configure the model and the maximum message and character counts under Dashboard → Settings → Reply suggestions. Available models are retrieved from the authenticated Claude Code SDK; Claude Code is currently the only suggestion provider; other providers are not supported yet. This may use your Claude account or incur provider charges. Swipe left or right through the results and select one to place it in the draft; sending still requires explicit confirmation. Suggestions are not supported for other agents yet and are not generated automatically.

### External Claude Code permission forwarding (experimental)

OpenGlassUI can forward `PermissionRequest` hooks from local Claude Code sessions that have already been imported. On macOS or Linux, enable it explicitly on the machine running Claude Code with `openglassui --enable-claude-hook` (or `node bin/openglassui.js --enable-claude-hook` from a checkout). This merges a hook into your user-level Claude settings, affecting local Claude Code sessions; it does not change permission rules or automatically approve requests. Review `~/.claude/settings.json` and remove the OpenGlassUI hook there to disable it. If `CLAUDE_CONFIG_DIR` is set, that directory is used instead. For a nondefault dashboard port set `OPENGLASS_PORT` for the Claude process.

Import the exact session and keep the companion connected. The hook waits up to 110 seconds for a paired-device answer. If the companion is unreachable, the session is not imported, or the wait expires, control returns to Claude's normal permission flow; no approval is issued. Claude's hooks do not cover every kind of dialog or sandbox network approval, and remote/cloud sessions on another machine need their own integration. Existing requests that appeared before enabling the hook cannot be captured retroactively. Support for Claude Desktop and real glasses requires device testing. See [Claude's hook reference](https://code.claude.com/docs/en/hooks#permissionrequest).

### Stable addresses across updates

Quick Tunnels are temporary and disabled for new selection in the interface; existing connections are not stopped. To keep the same glasses address, choose **Tailscale Funnel** in setup, enable the provider's HTTPS and Funnel prompts, and enable connection auto-start. Funnel publishes the gateway to the internet; the hostname remains the same while the device name and tailnet name remain unchanged. Test connectivity on the actual glasses: Funnel support on Meta glasses has not yet been verified. Tailscale Serve is private and may not be reachable by the glasses even when the phone can reach it. The managed tunnel reconnects when OpenGlassUI restarts; a restart causes a brief outage.

Alternatively, create a [named Cloudflare Tunnel](https://developers.cloudflare.com/tunnel/features/locally-managed-tunnels/create-local-tunnel/) or another independently managed HTTPS reverse proxy. Route only `http://127.0.0.1:4174` (or your configured gateway port), run it as its own service, and choose **Existing HTTPS address** in setup. Enter its HTTPS origin; OpenGlassUI saves it with the local setup and will not manage or stop that independent service. Do not expose port 4173. Changing from an old hostname requires one new pairing; the same stable origin and preserved device data keep pairing across ordinary updates. Local network access similarly requires a reachable HTTPS endpoint and a certificate trusted by the glasses; LAN-only connectivity is not yet verified.

The tunnel provider and optional automatic-start preference are stored in local setup. Automatic startup is off by default and starts only after completed setup when explicitly enabled. Cloudflare Quick Tunnel addresses change when restarted; update or re-pair the glasses app as needed. The Homebrew button is available only on macOS when Homebrew is in the companion’s PATH.

Both the admin service and gateway bind to `127.0.0.1`, not the local network. Tasks and their output are written to `.openglass/tasks.json` by default, including prompts and potentially sensitive agent output. Data is not encrypted at rest. Running tasks are marked interrupted after a server restart.

## Connect the glasses (experimental)

1. Enable the developer/web-app options required by Meta AI for your glasses.
2. Start OpenGlassUI and leave it running on the computer.
3. In the dashboard, select an installed tunnel provider and click **Tunnel starten**. For temporary testing only, an existing Quick Tunnel may also be started separately from a terminal with the default port:

   ```sh
   cloudflared tunnel --url http://127.0.0.1:4174
   ```

   Copy the HTTPS URL printed by cloudflared. If you changed `OPENGLASS_GATEWAY_PORT`, use that port in the command. Never forward the admin port. Cloudflare describes Quick Tunnels as a development feature; the address changes when the tunnel is restarted. See the [Quick Tunnel documentation](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/).

   For private access, select **Tailscale Serve** instead. Install and sign in to Tailscale on the companion and iPhone, enable HTTPS in the tailnet, and allow access under your tailnet policy. Tailscale is required only for this option, not when using Cloudflare or ngrok. The dashboard starts foreground `tailscale serve` for the gateway; stopping it ends that foreground service. A conflicting existing Serve configuration may need separate attention. The glasses' ability to reach a private tailnet address through the iPhone has not been verified; connecting from the iPhone alone does not prove glasses connectivity. If the glasses report that the app cannot load, try the generated app URL on the iPhone first; an iPhone-only success still does not establish glasses access. For an initial device test, a publicly reachable HTTPS tunnel follows Meta's documented web-app deployment path. See [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve).
4. In the desktop dashboard, paste that address into **ÖFFENTLICHE HTTPS-ADRESSE** and choose **Kopplungscode erzeugen**.
5. Scan the QR code with the iPhone, follow the Meta AI app's add-web-app flow, and open OpenGlassUI on the glasses **within five minutes**. The pairing code can be redeemed once. This deep-link flow is implemented but has not been verified on the actual device.
6. Keep the companion and tunnel running while using the app. An Internet connection is needed for the tunnel; the glasses and computer do not need to be on the same LAN when the HTTPS endpoint is reachable.

The glasses page organizes agents, projects and chats into navigable screens, with a conversation view and settings. It uses authenticated WebSocket revision events with long-poll fallback and implements geometry-based directional navigation and Select. Text fields use the host's standard text composer; Meta documents handwriting and voice composition on supported glasses. Camera attachments are not implemented. In settings, a paired device can optionally subscribe to standard Web Push after the wearer grants browser permission. The implementation has mock-based tests, but Web Push availability and delivery on Meta glasses have not been established. Meta documents that WebMCP tools are available only while the web app is in the foreground, with a 10-second call deadline. It also registers experimental WebMCP tools when `document.modelContext` is available. The complete navigation, text composition and gestures need a real-device test. See [Meta's web-app input guidance](https://github.com/meta/meta-wearables-webapp/blob/main/plugins/meta-wearables-webapp/skills/ai-glasses-webapp-device/SKILL.md).

The chat composer presents dictation or handwriting as the primary action. Select the field to open the device's composer; a web page cannot open it automatically. Back navigation handles Escape and browser history, restores the originating focus and scroll position, and leaves Backspace available for text editing. The thumb-to-middle-finger back gesture was confirmed by a wearer on their device. Meta documents the thumb-to-middle-finger gesture for back navigation; behavior in the device composer and on physical glasses still needs verification. Usage and tool activity are hidden by default and can be enabled in glasses settings. Read-aloud is also off by default; manual and automatic playback depend on the device browser's speech synthesis support, which has not yet been verified on Meta glasses.

The glasses interface offers English and German in Settings → Interface language, independently of the speech language. Agent messages and user text are not translated. Some server and provider errors may still use their original language. Settings → Theme offers Default, Hacker, Light and Dark; the dashboard and public demo have their own theme selectors. Preferences are stored in each browser origin, so the glasses and companion can use different themes. Light mode's readability on the additive glasses display has not been verified.

When speech synthesis is available, the glasses settings offer device-default, German and English speech languages. OpenGlassUI requests a matching device voice if one is reported; available voices and accents depend on the device, and the selection does not translate the response.

The glasses home screen can show recent OpenGlassUI-managed chats across selected agents and approved projects. Device settings control visibility, the maximum number (3, 5 or 10), and the last-message window (6, 24, 72 or 168 hours). Running tasks and pending decisions take priority regardless of age. Last-message timestamps are recorded for new activity; older records fall back to their creation time. Sessions in other clients appear only after being opened in OpenGlassUI.

After setup is completed, subsequent visits open the dashboard directly; the setup wizard and connection controls are under **Settings & setup**. **Linked devices** lists paired devices (not their current online status) and can create a new single-use pairing QR code. The **Glasses preview** uses the same wearable interface and real local data, so actions in it can control agents. The GitHub Pages dashboard demo instead uses fictional in-memory data and cannot connect to agents or devices. The wearable home screen shows the package version. Configuration, paired-device records and task history are stored locally in the ignored `.openglass` directory (or `OPENGLASS_DATA_DIR`), currently as JSON rather than SQLite. The dashboard counts locally stored tasks, pending decisions and prompts sent through OpenGlassUI since message tracking was introduced. It does not count historical messages or activity in other clients. Token and cost figures are shown per task only when reported by the provider; their scope varies by provider. Effective agent permissions and comprehensive MCP usage are not currently available. This activity information stays local to the companion and is not sent to an analytics service.

The gateway also serves Meta's `/.well-known/meta-wearables-manifest.json` and a monochrome glasses icon for the launcher. An existing installation may need to be removed and added again to refresh its icon; actual launcher rendering has not yet been verified on hardware. See Meta's [app icon utility](https://github.com/meta/meta-ray-ban-display-ui-toolkit-web/tree/main/examples/app-icon-generator).

## Security and privacy

**This is an experimental single-user prototype, not a hardened remote-access service.** The OpenGlassUI companion contains no built-in analytics or telemetry sent to an OpenGlassUI-operated service. Connected agents, model providers, device software, tunnel services, optional push providers, and package hosts can communicate externally under their own policies.

- The companion binds to localhost. Remote access depends on a correctly configured HTTPS reverse proxy. The companion separates the admin listener from a paired-device gateway. Forward only the gateway port through a tunnel; never publish the admin port. A malicious local process can still access the admin listener, and this design is not a formal security audit.
- A pairing QR contains a short-lived secret. Anyone who redeems it can read accessible tasks and sessions and launch configured agents with the permissions of the local user. Treat the QR and installation link like a password; do not share screenshots or logs containing them.
- The companion issues a bearer token to a paired device. It is stored in that device's browser storage and is not hardware-bound. Its hash and device metadata persist locally until revoked. Revoke devices individually or use **Alle Verbindungen trennen** in the local dashboard. The token grants access to all registered projects and tasks.
- Optional Web Push stores a browser push subscription and local VAPID private key in the protected data directory; the browser push provider receives encrypted generic event notifications and connection metadata. Payloads contain no project names, prompts, paths, or agent output. Only supported browser-vendor push endpoints are accepted. Delivery requires a running companion and is not guaranteed. The local dashboard reports provider acceptance or failure; acceptance does not prove the wearer saw the notification, and already queued messages can arrive briefly after revocation. Browser support, permission behavior, and background delivery on Meta glasses are unverified. Revoking a paired device removes its server-side subscription.
- Remote task data and agent outputs pass through the HTTPS tunnel provider. Local task data is stored without encryption. Consider what code, prompts, and output the agent and tunnel provider can access.
- Approvals are per request where supported. Existing agent configuration may already allow actions without a prompt. OpenGlassUI does not guarantee a separate confirmation for every action.

### Wearable navigation

The wearable home screen puts pending decisions and running tasks before recent chats and agents. Arrow keys (or supported band navigation) move focus; select activates an item and Back returns to the previous view. Composer actions are laid out horizontally, and the device provides its own dictation or handwriting composer. Review a dictated message and select Send explicitly. Long messages are split into navigable sections with speaker labels. Selecting an assistant section reads from that point onward when device speech is available; select again to pause or resume. Permissions show their tool details and require an explicit choice. Voice playback and the exact gesture behavior still require validation on the target glasses.

## Current technical gaps

- **Physical device validation:** QR deep link, setup, layout, focus order, wristband gestures, text input, WebMCP, reconnection, and long-running use need testing on actual Meta Ray-Ban Display hardware.
- **Installation and hosting:** Setup scripts and on-demand tunnel start exist, but no signed native installer, automatic updates, stable hosted URL, system-wide service, or managed reverse-proxy access control. Tunnel clients must be installed and ngrok authenticated separately.
- **Sessions:** No reliable live takeover of sessions running in other clients, no full transcript pagination, and no full transcript navigation or search. Generic CLI sessions cannot currently be resumed through the app.
- **Questions and permissions:** Simultaneous requests are queued per task and displayed one at a time; complete multi-select handling is still missing. Not every Codex server-request type is supported. AI-generated choices depend on the agent and may be absent.
- **Security:** No hardware-bound credentials, encrypted client storage, granular authorization, formal security review, or production-grade proxy authentication. The current deployment must remain a trusted, experimental single-user setup.
- **Reliability and UX:** No agent health checks, task deletion, reliable child-process-tree termination, comprehensive accessibility testing, or English UI. Kiro and Codex tool events are shown as a bounded per-task timeline; Claude and generic CLI agents do not yet have structured timelines. Outputs are bounded and may be truncated.
- **Testing:** Automated tests simulate agent decision paths and tunnel processes. A real Kiro task through the companion API, tool events, context usage, session list, and continuation were checked locally; a real Claude account, end-to-end tunnel traffic, WebMCP, simulator interaction, and physical glasses still need verification. Cloudflare Quick Tunnel startup was exercised locally against an isolated test target.

## Tests

```sh
npm test
```

The suite exercises the local API, project allowlist, pairing and revocation, separate gateway, authenticated WebSocket revocation, tunnel manager, opt-in Web Push validation and mock delivery, simulated Codex, Claude and Kiro decision handling, a paired Kiro event-to-decision flow, foreground-notification transitions, spatial navigation logic, usage formatting and voice-tool validation. It requires permission to bind a localhost port. A successful suite is not a substitute for hardware or provider end-to-end testing.

If Claude reports that its OAuth session has expired, authenticate again using the supported Claude Code login flow, for example `claude auth login` where available, then retry. OpenGlassUI does not request or store your Claude password.
